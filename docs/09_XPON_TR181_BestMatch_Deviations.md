# 09 — `Device.XPON` Best-Match Mappings and BBF Deviations

This document lists every supported `Device.XPON` parameter whose value does **not** match its BBF TR-181 2.21 definition exactly. For each one it explains why, and what would make it compliant.

- **Scope:** the 89 supported `Device.XPON` parameters in [08_TR181_Telemetry_Reference.md](08_TR181_Telemetry_Reference.md) §1.1. Parameters that are not supported at all are listed in Appendix A of that document.
- **Implementation:** `source/TR-181/rbus/tr181/gponmgr_xpon_tr181.c`.
- **Reference:** BBF TR-181 Issue 2 Amendment 21 (`tr-181-2-21-0-cwmp-full.xml`).
- **HAL fixes:** proposed HAL changes are in [10_HAL_Schema_Extensions.md](10_HAL_Schema_Extensions.md) and are referred to as **EXT-n**.

## Categories

| Category | Meaning |
|---|---|
| **Best match** | The value comes from the closest field the RDK HAL provides, but that field is defined differently from the BBF parameter (different source register, scope or counting rule). |
| **Value deviation** | The reported value, enumeration or counter behaviour differs from what BBF defines. |
| **Access deviation** | BBF defines the parameter as writable; GPON Manager makes it read-only. |
| **CPE-assigned (compliant)** | The value is a constant or is generated by GPON Manager. BBF allows this. It is listed here only so readers do not mistake it for HAL data. |

## 1. Best-Match Mappings

### 1.1 `TC.PM.PHY.HeaderHECErrorCount` ← `X_RDK_ONT.Gtc.HecErrorCount`

| | |
|---|---|
| **BBF** | HEC errors received in the downstream XGTC header (XG-PON) or framing sublayer (FS) header (XGS-PON / NG-PON2). StatsCounter32. |
| **HAL** | `Gtc.HecErrorCount`, an unsignedInt described only as a "HEC error count". |
| **Why best match** | The RDK HAL does not say which header the count covers. On G-PON there is no XGTC/FS header, so the vendor may count a GTC header error instead. |
| **To close** | The vendor confirms that `HecErrorCount` counts DS XGTC/FS header HEC errors. No schema change is needed. |

### 1.2 `TC.PM.GEM.FrameHeaderHECErrors` ← `X_RDK_ONT.Gtc.FrameHecErrors`

| | |
|---|---|
| **BBF** | XGEM frame header HEC errors: the number of events involving loss of XGEM channel delineation. StatsCounter32. |
| **HAL** | `Gtc.FrameHecErrors`, an unsignedInt. |
| **Why best match** | The HAL name suggests (X)GEM frame-header HEC errors, but the HAL does not define whether it counts *errors* or *delineation-loss events*. |
| **To close** | Vendor confirmation. |

### 1.3 `Transceiver.{i}.VendorPartNumber` ← `X_RDK_ONT.PhysicalMedia.{i}.ModuleName`

| | |
|---|---|
| **BBF** | Vendor part number: the SFF-8472 "Vendor PN" field (A0h bytes 40–55, 16 ASCII characters). |
| **HAL** | `ModuleName`, the module *model name* (Broadcom: max 64 characters). |
| **Why best match** | It is the closest field the HAL has. On the Sercomm XF10 both values are the same (`XF10`), but nothing guarantees that the model name equals the EEPROM part number on other modules. |
| **To close** | EXT-9: expose the raw SFF-8472 Vendor PN. |

### 1.4 `Transceiver.{i}.VendorRevision` ← `X_RDK_ONT.PhysicalMedia.{i}.ModuleVersion`

| | |
|---|---|
| **BBF** | Vendor revision: the SFF-8472 "Vendor rev" field (A0h bytes 56–59, 4 ASCII characters). |
| **HAL** | `ModuleVersion`, the module *hardware version* (max 64 characters). |
| **Why best match** | Same reason as 1.3. A value longer than 4 characters cannot have come from the EEPROM field. |
| **To close** | EXT-9. |

### 1.5 `TC.GEM.Port.{i}.PortType` ← `X_RDK_ONT.Gem.{i}.TrafficType` (heuristic)

| | |
|---|---|
| **BBF** | `unicast`, `multicast` or `broadcast`. |
| **HAL** | Only `TrafficType` (`Bidirectional` / `Unidirectional`). |
| **Mapping** | `Bidirectional` → `unicast`, `Unidirectional` → `multicast`. `broadcast` is never reported. |
| **Why best match** | The RDK HAL schema has no port-type field. In practice unidirectional GEM ports are downstream multicast or broadcast ports, so a broadcast port is reported as `multicast`. |
| **To close** | EXT-1: `Gem.{i}.Type`. Broadcom already sends it to GPON Manager, which currently discards it. |

## 2. Value Deviations

### 2.1 `TC.GEM.Port.{i}.Direction` reports `unidirectional`

| | |
|---|---|
| **BBF enumeration** | `UNI-to-ANI`, `ANI-to-UNI`, `bidirectional`. |
| **Reported** | `bidirectional` for a Bidirectional port, `unidirectional` for a Unidirectional port. |
| **Why** | The HAL says that a port is one-way but not which way. `unidirectional` was chosen deliberately rather than guessing a direction or failing the get. |
| **To close** | EXT-10 (explicit G.988 direction), or EXT-1. With EXT-1, a Unidirectional port of type `multicast`/`broadcast` can be reported as `ANI-to-UNI`, because multicast and broadcast GEM ports are downstream-only. |

### 2.2 `TC.ONUActivation.ONUState`: `O2-3` is never reported

| | |
|---|---|
| **BBF enumeration** | `O1`, `O2`, `O3`, `O2-3`, `O4` … `O9`. |
| **Standards** | G-PON (G.984.3) has separate O2 (Standby) and O3 (Serial-Number) states. XG-PON, XGS-PON and NG-PON2 (G.987.3, G.9807.1, G.989.3) merge them into one state, **O2-3**. |
| **Reported** | HAL state 2 → `O2`, 3 → `O3`, whatever the PON mode. |
| **Impact** | On this XGS-PON device, a strictly BBF-compliant ACS would expect `O2-3`. |
| **To close** | In GPON Manager, report `O2-3` for HAL states 2 and 3 when `PONMode` is XG-PON, XGS-PON or NG-PON2. The telemetry `From=`/`To=` values would need the same change. **Not implemented yet; needs a decision.** |

### 2.3 `TC.PM.GEM.FramesSent` / `FramesReceived` are sums of per-port counters

| | |
|---|---|
| **BBF** | ANI-wide (X)GEM frame totals, StatsCounter64, which must only increase until reset. |
| **Reported** | Σ `Gem.{i}.TransmittedFrames` / `ReceivedFrames` over the GEM ports that currently exist. |
| **Why** | The HAL has no ANI-level GEM counter. |
| **Impact** | The total **drops** when the OLT removes a GEM port, which violates StatsCounter monotonicity. Broadcom's per-port `TransmittedFrames` is also 32-bit, so a single port can wrap. |
| **To close** | Add an ANI-level GEM frame counter to the HAL (Tier 3, not in the Broadcom DM), or have GPON Manager keep a running total that survives port removal. |

### 2.4 `EthernetUNI.{i}.Stats.BytesSent` / `BytesReceived` exclude framing

| | |
|---|---|
| **BBF** | Total bytes, *including framing characters*. |
| **Reported** | Linux `/sys/class/net/<veip>/statistics/tx_bytes` / `rx_bytes`. |
| **Why** | The kernel counts the Ethernet frame without the preamble and FCS. |
| **Impact** | Values are slightly lower than a framing-inclusive count, by up to 12 bytes per frame (8-byte preamble + 4-byte FCS). The other EthernetUNI counters are frame counts and are not affected. |
| **To close** | EXT-6 (G.988 VEIP Ethernet PM `Octets`), if its counting rule includes the FCS. Otherwise accept as documented. |

### 2.5 `LastChange` restarts at 0 when GPON Manager restarts

| | |
|---|---|
| **BBF** | Accumulated seconds since the interface entered its current operational state. |
| **Reported** | Seconds since GPON Manager last saw `Status` (ANI) or `OperationalState` (EthernetUNI) change. The time is taken from `CLOCK_MONOTONIC` when the HAL push event or poll reports the change, or when the row is created. |
| **Why** | The HAL `PhysicalMedia.LastChange` is not pushed with events, and VEIP has no LastChange at all. |
| **Impact** | After a GPON Manager restart the value starts again from 0, even though the link did not change. This is the usual behaviour for RDK component-computed LastChange values. |
| **To close** | No change needed. |

### 2.6 `Transceiver.{i}.Temperature` precision

| | |
|---|---|
| **BBF** | int, whole °C. |
| **HAL** | `Temperature.CurrentTemp` in 0.1 °C (Broadcom unit). |
| **Reported** | Rounded to the nearest whole °C (e.g. 470 → 47). HAL values below −2740 are rejected. |
| **Impact** | Compliant; the 0.1 °C resolution is lost. The raw value remains available in `X_RDK_ONT.PhysicalMedia.{i}.Temperature.CurrentTemp`. |

### 2.7 `Transceiver.{i}.Identifier` is not available on bond-on-board (BoB)

| | |
|---|---|
| **BBF** | SFF-8024 identifier byte. |
| **Reported** | `3` (SFP/SFP+/SFP28) when the HAL `Cage` is `SFP`. The get is rejected for `BoB`, because a soldered optic has no SFF-8024 identifier. |
| **Impact** | None on the XF10, which uses an SFP. |

## 3. Access Deviations

BBF defines these parameters as writable. GPON Manager makes them read-only; a set returns `RBUS_ERROR_NOT_WRITABLE`.

| Parameter | BBF access | Reason |
|---|---|---|
| `ONU.{i}.Enable` | R/W | Disabling the ONU would take the WAN down. The value is also used to show HAL health: `true` while the JSON-HAL client is connected to the vendor HAL server. That is a **semantic deviation**: BBF means the administrative enable of the ONU. |
| `ANI.{i}.Enable` | R/W | Writing `false` forces the ONU to O1 and drops the PON link. The value comes from HAL `PhysicalMedia.{i}.Enable`. |
| `ANI.{i}.Alias` | writeOnceReadOnly | The value comes from HAL `PhysicalMedia.{i}.Alias`. GPON Manager has no persistent store for an ACS-written alias. |
| `EthernetUNI.{i}.Alias` | R/W | Generated as `cpe-` + the upper-case VEIP interface name. |
| `EthernetUNI.{i}.Description` | R/W | Generated as `GPON VEIP WAN interface <Alias>`. |
| `EthernetUNI.{i}.LowerLayers` | R/W | Always empty. BBF says `LowerLayers` should not be used for EthernetUNI. |

**To close:** making Alias/Description writable needs a persistent store (e.g. PSM) and changes to the RBUS set handlers. Making Enable writable is not recommended on a single-WAN gateway.

## 4. CPE-Assigned Values (Compliant)

BBF allows these values; they are listed so that nobody mistakes them for HAL data.

| Parameter | Value | Note |
|---|---|---|
| `ONUNumberOfEntries`, `ANINumberOfEntries` | `1` | One ONU with one ANI. |
| `ONU.{i}.SoftwareImageNumberOfEntries` | `0` | The HAL has no software-image inventory (EXT-12). |
| `ONU.{i}.Name` | `ONU<i>` | BBF: "as assigned by the CPE". |
| `ANI.{i}.Name` | `ANI<i>` | BBF: "as assigned by the CPE". |
| `ANI.{i}.SFPReferenceList` | empty | `Device.SFPs` is not implemented on this platform. |
| `EthernetUNI.{i}.ANIs` | `Device.XPON.ONU.1.ANI.1` | Only one ANI. |
| `EthernetUNI.{i}.Upstream` | `true` | The VEIP is the gateway's WAN interface. |
| ANI-level `Status` / `PONMode` | from the single active PhysicalMedia row | If there is not exactly one active row, `PONMode` reports `Unknown` and the other ANI-level gets are rejected. |

1. TR-181 Data Model Parameters

GPON Manager exposes the standard BBF Device.XPON data model (TR-181 2.21) and the RDK extension model Device.X_RDK_ONT. This summary lists every supported Device.XPON parameter and the Device.X_RDK_ONT parameters that have no Device.XPON equivalent.

Legend: Read-Only Read/Write. Data types, enumerations, ranges and string sizes follow BBF TR-181 2.21. Descriptions are the BBF text; text in italics describes GPON Manager behaviour.
Instances: one ONU and one ANI (ONU.1, ANI.1). EthernetUNI.{i} has one row per VEIP interface, ANI.1.Transceiver.{i} one row per optical module and TC.GEM.Port.{i} one row per GEM port.
Value difference from BBF: TC.GEM.Port.{i}.Direction reports unidirectional (not in the BBF enumeration) for a one-way GEM port.
Read-only differences from BBF: ONU.{i}.Enable, ANI.{i}.Enable, ANI.{i}.Alias, EthernetUNI.{i}.Alias, EthernetUNI.{i}.Description and EthernetUNI.{i}.LowerLayers are writable in BBF but read-only in GPON Manager.

2. Telemetry Events (T2)

Events are sent through the RDK Telemetry 2.0 (T2) framework by component GponManager. Every marker starts with XPON_. Events with a value are sent as a string event (t2_event_s); events without a value as a count of 1 (t2_event_d).

Event-driven: events are raised only when the PON stack reports a change (ONU state, alarm, VEIP state), on a link transition, or on a lifecycle / error condition. Reading TR-181 parameters never raises telemetry, except the poll-failure events XPON_ERROR_STATS_COLLECTION_FAILED and XPON_SYSTEM_HAL_WRONG_PON_MODE.

2.1 ONU Activation (PLOAM) Events

Raised when the ONU activation state (Device.XPON.ONU.{i}.ANI.{i}.TC.ONUActivation.ONUState) changes. Every change sends XPON_ONU_STATE_CHANGE; some changes also send a milestone event (see §2.6).

2.6 ONU State → Event Mapping (XGS-PON)

XGS-PON (ITU-T G.9807.1, 10G symmetric) uses the activation state machine of G.989.3 without the wavelength-tuning states O8/O9. Serial-number acquisition is a single state, O2-3.

XPON_ONU_STATE_CHANGE carries the previous and new state as From=O<a>,To=O<b>, so every transition is identified by that value alone. Milestone events (XPON_ONU_*) follow it for the key transitions and are meant for simple dashboards.

Order of events: XPON_ONU_STATE_CHANGE is always sent first, then the matching milestones in this order: EMERGENCY_STOP_CLEARED (leaving O7), DOWNSTREAM_SIGNAL_DETECTED (leaving O1), LOS (entering O6, or O2–O5 → O1), DEREGISTRATION (leaving O5), REGISTRATION (entering O5), EMERGENCY_STOP (entering O7). No change, no event.
O2-3 reporting: TR-181 reports the XGS-PON state O2-3 as O2 or O3, depending on the PON stack. Both mean the same state and give the same milestones. In the telemetry value it therefore appears as O2 or O3.

2.6.3 Other Reported Pairs

Only the latest state is reported. When several transitions happen quickly, intermediate states are skipped and the pair is not one of the standard transitions above. Read it as the shortest standard path:
